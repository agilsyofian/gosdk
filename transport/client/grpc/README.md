# gRPC Client SDK

## Objective

Improve the existing Go gRPC client SDK into a reusable, production-grade transport layer with:

- Custom request-level headers / metadata
- System, security, and application header separation
- Context-based request metadata
- JWT token caching
- Safe authentication handling
- Retry and circuit breaker ordering
- Trace/log propagation
- Unary and streaming interceptor support
- Extensible interceptor architecture
- Protected security headers
- Clean client lifecycle management

The implementation must preserve backward compatibility where practical.

---

# 1. Core Design Principles

Follow these rules:

1. Static configuration belongs in `Config`.
2. Request-specific metadata belongs in `context.Context`.
3. Authentication metadata is generated by the authentication interceptor.
4. Security metadata such as signature and nonce is generated by the security interceptor.
5. Observability metadata such as trace IDs is generated by observability middleware/interceptors.
6. Application-specific headers are supplied through request context.
7. Protected headers must not be overridden by generic custom-header APIs.
8. Never panic from an interceptor because of an RPC/request error.
9. Do not generate a JWT on every RPC call.
10. Keep the gRPC client transport layer independent from business/domain services.

---

Refactor the gRPC package toward:

```text
transport/
└── grpc/
    ├── client.go
    ├── config.go
    ├── interceptor.go

    ├── metadata/
    │   ├── context.go
    │   ├── provider.go
    │   └── interceptor.go

    ├── auth/

    │   └── token_cache.go
    │
    ├── tracing/
    │   └── interceptor.go

    │
    └── resilience/

        └── circuitbreaker.go
```

The exact package structure may be adapted to the existing repository if equivalent separation already exists.

# 3. Request Metadata API

Implement request-scoped custom metadata.

Preferred API:

```go
ctx = grpcclient.WithHeader(ctx, "x-channel", "MOBILE")
ctx = grpcclient.WithHeader(ctx, "x-device-id", deviceID)
```

Also support bulk headers:

```go
ctx = grpcclient.WithHeaders(ctx, map[string]string{
    "x-channel":   "MOBILE",
    "x-device-id": deviceID,
    "x-client-id": clientID,
})
```

The metadata implementation must:

- Preserve existing outgoing metadata.
- Copy metadata before modification.
- Normalize header keys where appropriate.
- Avoid mutating metadata owned by another context.
- Be safe for request-level usage.
- Not store request-specific headers in the long-lived gRPC client object.

---

# 4. Header Categories

Define three categories.

## 4.1 System Headers

Managed by the SDK.

Examples:

```text
x-trace-id
x-request-id
x-session-id
traceparent
```

The SDK should be responsible for propagating these when available.

## 4.2 Security Headers

Managed by security/auth interceptors.

Examples:

```text
authorization
x-signature
x-nonce
x-timestamp
```

These must not be freely overridden by generic custom-header APIs.

## 4.3 Application Headers

Managed by the caller.

Examples:

```text
x-channel
x-device-id
x-client-id
x-language
x-platform
```

These are request-scoped and should be supplied through context.

---

# 5. Protected Headers

Create a centralized protected-header policy.

Example:

```go
var protectedHeaders = map[string]struct{}{
    "authorization": {},
    "x-signature":   {},
    "x-nonce":       {},
    "x-timestamp":   {},
    "traceparent":   {},
}
```

The exact list should be configurable internally if needed.

Generic APIs such as:

```go
WithHeader(ctx, "authorization", "...")
```

must not silently override SDK-generated security credentials.

Preferred behavior:

- Return an error for protected-header override, or
- Ignore the override deterministically and document the behavior.

Do not create ambiguous behavior.

---

# 6. Metadata Provider

Introduce an abstraction for dynamic metadata.

Example:

```go
type HeaderProvider interface {
    Get(ctx context.Context) metadata.MD
}
```

If useful, support function adapters:

```go
type HeaderProviderFunc func(context.Context) metadata.MD
```

This allows dynamic values:

```go
client.UseHeaderProvider(func(ctx context.Context) metadata.MD {
    return metadata.Pairs(
        "x-channel", getChannel(ctx),
        "x-device-id", getDeviceID(ctx),
    )
})
```

Providers should be composable.

---

# 7. Interceptor Ordering

Use a deterministic interceptor order.

Recommended logical order:

```text
Tracer
  ↓
Logger
  ↓
Circuit Breaker
  ↓
Retry
  ↓
Authentication
  ↓
Security / Signature
  ↓
Metadata
  ↓
RPC
```

The implementation may adjust the exact ordering based on gRPC interceptor semantics, but the final behavior must be documented and tested.

Important:

- Retry must not accidentally reuse invalid security metadata.
- If a signature uses nonce/timestamp, each retry must be evaluated carefully.
- A retry involving a signed request may require a fresh nonce/signature.
- Authentication should not generate a new JWT unnecessarily.

---

# 8. JWT Token Caching

Do not issue a new JWT for every RPC.

Implement a token provider/cache:

```text
RPC
 │
 ▼
Context token?
 │
 ├── valid → use
 │
 └── absent/expired
        │
        ▼
   Memory token cache
        │
        ├── valid → use
        │
        └── expired
              │
              ▼
         Singleflight
              │
              ▼
         Generate JWT
              │
              ▼
          Cache token
```

Requirements:

- In-memory cache.
- Configurable expiration/skew.
- Prevent concurrent token generation using singleflight or equivalent.
- Never panic on token-generation errors.
- Return the error to the RPC caller.
- Avoid unnecessary synchronization contention.
- Do not put access tokens into logs.

---

# 9. Authentication Interceptor

Authentication should be isolated:

```go
func Authorization(...) grpc.UnaryClientInterceptor
```

Responsibilities:

1. Read a valid token from request context if explicitly supplied.
2. Otherwise obtain a token from the token provider/cache.
3. Inject:

```text
authorization: Bearer <token>
```

4. Return authentication errors instead of panicking.

The interceptor should not own unrelated business headers.

---

# 10. Digital Signature Compatibility

The SDK must be designed to support future digital-signature middleware.

Example:

```text
Request
  ↓
Build canonical payload
  ↓
Generate nonce
  ↓
Generate timestamp
  ↓
Sign request
  ↓
Inject:
  x-signature
  x-nonce
  x-timestamp
  ↓
RPC
```

If retry occurs, define whether the signature is:

- regenerated per retry, or
- reused.

For anti-replay protection, prefer generating a fresh nonce/signature for each actual transmission when protocol semantics require it.

Do not implement signature logic inside generic metadata handling.

---

# 11. Trace and Session Propagation

Tracing/session middleware should read from context.

Examples:

```text
x-trace-id
x-request-id
x-session-id
```

Only inject values that are actually available.

Avoid generating multiple competing IDs across layers.

Prefer the existing OpenTelemetry trace context when available.

Do not log sensitive authentication metadata.

---

# 12. Unary and Streaming RPC

The SDK currently focuses on unary RPC.

Extend the architecture so it can support:

```go
grpc.UnaryClientInterceptor
grpc.StreamClientInterceptor
```

The client should maintain separate chains:

```go
type Client struct {
    conn                *grpc.ClientConn
    unaryInterceptors  []grpc.UnaryClientInterceptor
    streamInterceptors []grpc.StreamClientInterceptor
}
```

All applicable features should have a clear policy for streaming calls.

---

# 13. Client Lifecycle

Avoid misleading naming around `grpc.NewClient`.

The SDK should expose an explicit lifecycle.

Example:

```go
client := grpcclient.New(config)

conn, err := client.Connect(ctx)
if err != nil {
    return err
}

defer client.Close()
```

The exact API may differ if the existing SDK already has a strong convention.

Requirements:

- Explicit connection ownership.
- Explicit close behavior.
- No leaked connections.
- Safe repeated close.
- Clear behavior when RPC is called before connection establishment.

---

# 14. Configuration vs Request Context

Do NOT implement generic request headers like:

```go
type Config struct {
    Headers map[string]string
}
```

for values that change per request.

This is wrong for:

```text
x-device-id
x-session-id
x-request-id
x-signature
x-nonce
```

Use:

```go
ctx = grpcclient.WithHeader(ctx, key, value)
```

Configuration should contain only static/client-level configuration such as:

```go
type Config struct {
    Target              string
    Timeout             time.Duration
    Retry               RetryConfig
    CircuitBreaker      CircuitBreakerConfig
    Auth                AuthConfig
    TLS                 TLSConfig
}
```

---

# 15. Error Handling

Interceptors must never use:

```go
panic(err)
```

for expected runtime failures.

Use:

```go
return nil, err
```

or the equivalent interceptor return contract.

Errors should preserve enough context for:

- caller handling,
- observability,
- tracing,
- metrics.

Do not expose JWT, private keys, signatures, or sensitive metadata in error messages.

---

# 16. Retry Policy

Retry must be explicit and configurable.

Only retry appropriate errors.

Do not retry blindly on:

```text
InvalidArgument
Unauthenticated
PermissionDenied
AlreadyExists
FailedPrecondition
```

Typical retry candidates may include transient infrastructure failures such as:

```text
Unavailable
ResourceExhausted
DeadlineExceeded
```

depending on the RPC semantics.

Support:

- max attempts,
- backoff,
- max backoff,
- retryable status codes,
- optional jitter.

Avoid retrying non-idempotent operations unless the API explicitly guarantees safe retry semantics.

---

# 17. Circuit Breaker

Circuit breaker should operate at the transport/client boundary.

Requirements:

- Configurable failure threshold.
- Configurable open duration.
- Half-open support.
- Avoid treating normal business errors as infrastructure failures.
- Metrics for state changes.
- Clear interaction with retry.

Document whether circuit-breaker counting occurs:

```text
per attempt
```

or:

```text
per logical RPC
```

Prefer counting the logical RPC result rather than every retry attempt unless there is a strong reason otherwise.

---

# 18. Logging

Logging interceptor must not log:

```text
authorization
x-signature
x-nonce
private keys
JWT
session secrets
```

Recommended fields:

```text
service
method
duration
status
trace_id
request_id
retry_count
error_code
```

Payload logging must be opt-in and sanitized.

---

# 19. Observability

Expose metrics for:

```text
grpc_client_requests_total
grpc_client_request_duration
grpc_client_errors_total
grpc_client_retries_total
grpc_client_circuit_breaker_state
grpc_client_auth_token_refresh_total
```

Use OpenTelemetry where the SDK already has observability support.

Avoid creating a second independent tracing system.

# 21. Backward Compatibility

Do not unnecessarily break the existing SDK API.

If an API must change:

1. Introduce the new API.
2. Keep the old API temporarily where feasible.
3. Mark old APIs as deprecated.
4. Provide migration examples.
5. Remove only in a deliberate major version.

---

# 22. Acceptance Criteria

The implementation is considered complete when:

- [ ] Custom request-level headers can be added through context.
- [ ] Multiple custom headers are supported.
- [ ] Existing outgoing metadata is preserved.
- [ ] Protected headers cannot be overridden accidentally.
- [ ] Authentication is separated from generic metadata.
- [ ] JWT generation is cached and protected by singleflight/equivalent.
- [ ] No interceptor panics on normal runtime errors.
- [ ] Retry and circuit breaker behavior is deterministic.
- [ ] Signature/anti-replay can be added without redesigning metadata.
- [ ] Trace/session propagation remains supported.
- [ ] Unary and streaming interceptor architecture is supported.
- [ ] Sensitive metadata is excluded from logs.
- [ ] Client lifecycle is explicit and leak-free.
- [ ] Unit tests cover metadata, auth, retry, security, and lifecycle.
- [ ] Existing consumers remain compatible where practical.

---

# 23. Example Target Usage

The final SDK should make application code simple:

```go
ctx = grpcclient.WithHeaders(ctx, map[string]string{
    "x-channel":   "MOBILE",
    "x-device-id": deviceID,
    "x-client-id": clientID,
})

resp, err := userClient.GetUser(ctx, req)
if err != nil {
    return err
}
```

Application developers should NOT need to manually construct:

```go
metadata.NewOutgoingContext(...)
```

for normal custom-header use cases.

Security-sensitive metadata should remain automatic:

```text
authorization
x-signature
x-nonce
x-timestamp
```

and should be managed by SDK interceptors.

# 24. Implementation Priority

Implement in this order:

### Phase 1 — Metadata Foundation

- Context-based headers.
- Bulk headers.
- Metadata merge.
- Protected-header policy.
- Header provider abstraction.

### Phase 2 — Authentication

- Token provider.
- In-memory token cache.
- Singleflight refresh.
- Authorization interceptor.

### Phase 3 — Interceptor Architecture

- Deterministic interceptor ordering.
- Unary + stream support.
- Retry integration.
- Circuit breaker integration.

### Phase 4 — Observability

- Trace propagation.
- Structured logging.
- Metrics.

### Phase 5 — Security Extension

- Digital signature provider.
- Nonce provider.
- Anti-replay integration.
- Retry-aware signature regeneration.

### Phase 6 — Testing & Compatibility

- Unit tests.
- Integration tests.
- Backward compatibility.
- Documentation and examples.

# 25. Important Constraint

Do not over-engineer the first implementation.

The primary goal is a clean extension point:

```text
Context
  ↓
Metadata
  ↓
Interceptors
  ↓
gRPC
```

The architecture must make future additions such as:

```text
JWT
JWKS
Digital Signature
Anti-Replay
mTLS
OAuth
Tracing
Metrics
```

possible without changing the application-facing gRPC service code.
